# Do FCD's other cartridges use the same ciphers? (Xplorer64)

`FCD.md` and `ENCRYPT.md` leave one question open by their own framing: the `.fcd`
image cipher and the WHBX/FCD!/WB123 code cipher were recovered from the PSX
product. FCD shipped others. This is the N64 one, **Xplorer64**, checked against
xpcrypt's two ciphers and its COMP01 container.

Short answer: **the container and the code cipher crossed over, and so, on the
evidence of one third-party tool, did the image cipher.**

* **Code cipher.** The N64 cheat database stores its codes encrypted with PSX key
  6 on bytes 1-5, `(x - 0x55) ^ i`. Only byte 0 differs: the N64 XORs it with
  `0x68` where the PSX keeps `x & 0xF0`. The published N64 routine (hammerhead,
  from kodewerx) says so, and the six firmware dumps' own databases bear it out
  (§4). The PSX seeds WHBX/FCD!/WB123 - keys 4, 5 and 7 - appear nowhere in the
  N64 firmware.
* **Image cipher.** The official 1.067G upgrade file is *plaintext*. But X-Killer,
  a third-party tool, recognises an "FCD N64 ROM - Encrypted" format by exactly
  the PSX `.fcd` cipher (§1). No such file is in hand.
* **COMP01.** It is shared, and so are the resources: at least eight streams decode
  to the same bytes on both consoles, most of them byte-identical even packed.
  One more is the same resource stored in the other byte order (§3).
* **The address scramble.** On the chip itself the N64 adds something the PSX does
  not have: a hardware address-line permutation, which moves bytes and never
  changes them (§2).

So xpcrypt's `-r` would apply to an encrypted N64 ROM if one turned up, and the
key-6 equations are the N64's, but `-e`/`-d` do not handle N64 codes as they
stand: byte 0 is treated differently, and nothing here reads the N64 code format.

Nothing here changes the shipped source. It records what crossed product lines.

## Where the files are

Not in the tree (like `roms/` and `pc/`, these are firmware dumps). Sources:

* `research/pc/x-killer.exe`, already in the PSX corpus (`FCD.md` §4).

## 1. Distribution: plaintext in hand, an encrypted format on record

The PSX contract is: the vendor ships a `.fcd`, which is the plaintext ROM run
through the value cipher (`dec[i] = (enc[i] ^ mask(i)) + addend(i)`,
`mask(i) = i ^ ((i>>1)+0x45)`), and the PC tool decrypts it before flashing
(`FCD.md`). The one official N64 upgrade in hand has no such step. It is
plaintext firmware:

```
XP64.ROM  262144 bytes
  offset 0x00  "(C) 1997/9 FCD Release 1.067G ..."   28 43 29 20 31 39 39 37 2f 39 20 46 43 44 ...
  9x COMP01 inside
  md5(XP64.ROM) == md5(sharkdumps xplorer64-v1.067g-b1930 .bin, the *unscrambled* dump)
```

The upgrade file the user flashes is the unscrambled image byte for byte.

That does not mean FCD never encrypted an N64 ROM. X-Killer's file-type
classifier (`0x4083D0`) has two N64 cases:

```
0x40840D  cmp edx, 0x200 ; jbe ...          longer than 0x200 bytes
0x408415  [0x200] == 'X' and [0x40] == 'F'  -> 5   FCD N64 ROM - Decrypted
0x408428  [0x200] == 0x69 and [0x40] == 0x3F -> 6  FCD N64 ROM - Encrypted
```

`'X'` at `0x200` and `'F'` at `0x40` are the plaintext N64 image's own marks
(`"Xplorer64 is not endorsed..."` at `0x200`, `"FUTURE CONSOLE DESIGN"` at
`0x40`). `0x69` and `0x3F` are exactly those two bytes under the PSX cipher (mask
`0x45`, addend `0x2C` at `0x200`; mask `0x25`, addend `0x2C` at `0x40`). `FCD.md` §4
has the rest:
the loader that accepts the encrypted type decrypts it with the same routine,
`0x408350`. X-Killer is Tim Schuerewegen's tool, not FCD's, so this shows what its
author believed about a format he had seen, not an FCD file. No encrypted N64 ROM
is in hand to check it against.

## 2. The scramble is on the address bus, not the bytes

What *is* scrambled is the physical EEPROM contents, and the scramble is a
permutation of the low address bits with some inverted — a CPLD wiring trick, not
a computation on the data. From `Unscramble.py`, applied per chip:

```python
def scramble(addr):
    return (((~addr >> 8) & 0x001) | ((~addr >> 5) & 0x006) | ((~addr >> 6) & 0x008)
          | ((addr << 4) & 0x010) | ((addr >> 6) & 0x020) | ((addr << 3) & 0x040)
          | ((addr << 2) & 0x080) | ((~addr >> 2) & 0x100) | ((addr << 8) & 0x200)
          | ((addr << 6) & 0x400) | ((~addr << 9) & 0x800) | (addr & 0x1F000))
```

Bits 0-11 are permuted, some inverted, and bits 12-16 pass through. The 256 KB
image is two 128 KB SST29LE010 chips **interleaved byte by byte**: even file
offsets on one, odd on the other. The permutation applies to each chip's own
address. Reimplemented from the formula above, it turns each of the five
`.scrambled.bin` dumps into its plain `.bin` exactly, and both files of each pair
have the same byte histogram: byte values stay, byte positions move. The
`.scrambled.bin` dumps have no readable `FCD`/`Release` string; the `.bin` dumps
do.

The distributed upgrade image is already in address order. Reading the
cartridge through the bus gives that order back, because the CPLD unscrambles on
the way out. Writing is not symmetric. RWeick's README says a writer has to
transform the addresses itself, and drive an even/odd write sequence chosen by
address parity. So whatever programs the chips - FCD's upgrader, or a cart reader
- has to know the permutation. This is the opposite shape from the `.fcd` cipher,
which leaves positions alone and transforms every byte.

## 3. COMP01 crossed over, and so did the resources

The N64 firmware is packed with the same COMP01 container `REVERSING.md` §4
documents on the PSX: nine streams in each 1.067 build, sixteen in each 1.000E.
`comp01.py` decodes all of them to their declared sizes. The header is `"COMP01"`
+ four escape bytes + a 4-byte big-endian size, and the escape bytes are stored
masked with `"Hugh"` (`REVERSING.md` §4.1). The escape values are chosen per
stream from the data (`FINDINGS.md` §5.1b).

The PSX streams below are *inside* the firmware, so they are found in the unpacked
image (`fwimage.load`), not in the ROM file. At ROM file offsets the same header
bytes do turn up - in `xteng.dec` at `0x15BCF` - but there they are literals of
the outer stream, and decoding from them gives garbage. The comparison is of
decoded output, with the packed bytes compared as well:

```

COMP01 Jvcm  0x0514   0x0514  xteng 0x211B3 xtepro 0x233AF          1.067E 0x22D94         same in xtepro, USA
                              USA 0x212A5                           1.000E 0x17944         and both N64
COMP01 Jvcm  0x1C08   0x1C08  xteng 0x20C4A xtepro 0x22E46          1.067E 0x22824         same in xtepro, USA
                              USA 0x20D3C                           1.000E 0x173D4         and both N64
COMP01 Jvcm  0x5320   0x5320  USA 0x20324                           1.067E 0x21E04         re-packed, same output
                                                                    1.000E 0x169B4
COMP01 `\MC  0x1142   0x1142  xteng 0x2A4A3 USA 0x2A2A3             1.067E 0x23DB4         identical
                                                                    1.000E 0x21B94
COMP01 Jvcm  0x14AE   0x14AE  xteng 0x26EA4                         1.000E 0x1E5D4         identical
COMP01 Jvcm  0x154E   0x154E  xteng 0x2172C xtepro 0x23928          1.000E 0x17EE4         same as xtepro
                              USA 0x2194B
COMP01 Jvcm  0x165C   0x165C  xteng 0x21264 xtepro 0x23460          1.000E 0x17A04         identical
                              USA 0x21483

                              USA 0x216B7
```

Eight resources decode to the same bytes on both consoles, and seven of them are
the same packed stream byte for byte in at least one PSX image. The same COMP01
encoder compressed the same resources for both cartridges. That is the concrete
evidence that the container and its resource set are one codebase across the
product line, not two lookalikes.

One stream that looks shared is not quite:

```
COMP01 Iwda  0x0400   PSX: xteng 0x20024, xtepro 0x22220, USA 0x2011C, xtger 0x20920,
                           xtjpro 0x21DD4, 2.005 0x1FCD0      (one 1024-byte output)
                      N64: 1.067E 0x21BF4, 1.000E 0x167A4     (a different output)
```

The N64 output is the PSX output with every 16-bit word byte-swapped: the same
resource, written for a big-endian CPU. They differ in 566 of 1024 bytes, and the
two packed streams share only their first 17 bytes. The headers match because
byte-swapping keeps the byte histogram, and the escapes are chosen from it. So
an identical header does not mean an identical stream. (`Iwda` and `Jvcm` are the
stored bytes; unmasked with `"Hugh"` the escapes are `01 02 03 09` and
`02 03 04 05`.)

## 4. The code cipher crossed over: PSX key 6

The PSX cheat-code cipher has four normal keys (`REVERSING.md` §6). Key 4 is
seeded with `"WHBX"`, key 5 with `" WB123"` and key 7 with `"FCD!"`. None of the
three appears anywhere in the N64 firmware, raw or in any of its unpacked COMP01
streams, in any of the six builds. Key 6 has no seed:

```
PSX key 6, bytes 1-5      o[i] = (c[i] - 0x55) ^ i                       (romcrypt.py)
N64 DecryptCodeMethod2    a[i] = (a[i] + 0xAB) ^ i              = the same, 0xAB == -0x55
N64 DecryptCodeMethod1    a[i] = (a[i] + 0x2B) ^ (0x80 + i)     = the same again
byte 0                    PSX: c[0] & 0xF0      N64: a0 ^ 0x68
```

hammerhead implements the two N64 methods as different functions. They are not:
`^ (0x80 + i)` for `i` = 1-5 is `^ 0x80 ^ i`, and `^ 0x80` is `+ 0x80` on a byte,
so Method1 adds `0x2B + 0x80 = 0xAB`. A brute-force check over every byte value
and position agrees, for both the decrypt and the encrypt forms.

That is hammerhead's account. The firmware's own data checks it. The N64 database
at `0x30000` has the PSX layout - game name, cheat count, cheat name, line count,
six-byte codes - and that is how hammerhead's reader walks it. Parsed that way it
runs cleanly to the erased flash in all six builds, with zero-line cheats used as
section headings (1.067G: 121 games, 2,615 cheats, 2,907 code lines). Most stored
codes begin `E8`. Under byte 0 `^ 0x68` and key 6 on bytes 1-5, an `E8` row
becomes an `80` row, the N64 8-bit write. Across the six builds:

```
rows stored as E8                          3,630
  decrypted address byte 1 < 0x40          3,598   (RDRAM, 0x80000000-0x803FFFFF)
  decrypted value high byte == 0x00        3,619   (an 8-bit write)
  raw address byte 1 < 0x40                    0
```

The other common stored bytes map to `C8` → `A0`, `ED` → `85`, `EB` → `83` and
`E3` → `8B`. All four are on hammerhead's opcode list, though it marks them
undocumented. So key 6 is the N64 code cipher in the shipped data, not only in a
later tool. What is *not* in hand is the N64 firmware's own decrypt routine. A
scan of the raw and unpacked 1.067E image for an R4300 `xori ..., 0x68` found
none, and the routine was not looked for further.

What did not cross over is the seeded keys 4, 5 and 7, and the key nibble. In
hammerhead's reading byte 0 carries no key at all: it is XORed with a constant,
and a code counts as encrypted when its first byte is not a known opcode.

## 5. The team, expanded

The PSX header credit is `"FCD = WHB PJH DN MW IN R?"` (`REVERSING.md` §1; the USA
2.004 copy reads `RM`). The N64 firmware spells it out, and the list grows with
the builds:

```
1.000E (both)           The people at FCD are WHB, PJH, DN, MW, IN, RM, and SPGM
1.067E (both)           The people at FCD are WHB, PJH, DN, MW, IN, RM, SPGM, and SK
1.067G, 1.067U          The people at FCD are WHB, PJH, DN, MW, IN, RM, SPGM, SK and MF
all                     (c) 1997/9 Future Console Design, Ltd
all                     Xplorer64 is not endorsed, licensed nor authorized by Nintendo Co Limited
```

WHB is still first — Wayne Hughes Beckett, whose initials seed the PSX cipher. The
N64 confirms that the PSX `R?` is `RM`.

The FX firmware's own boot descrambler (`FINDINGS.md` §5.4) is a property of the
PSX ROM's contents, not of its distribution, so it is not in the table.

## Open

* **The N64 firmware's code-decrypt routine** was not found. The cipher rests on
  hammerhead's source and on the shipped databases fitting it (§4), not on the
  routine itself.
* **An encrypted N64 ROM.** X-Killer is the only evidence that one existed; no file
  is in hand.
* **The N64 code format beyond byte 0.** What, if anything, replaces the PSX key
  nibble, and which opcodes the N64 engine implements, was not read.
* The Game Boy Color Xplorer (`GbcXpRom.cs`) is a third product line, unlooked-at.
