# Do FCD's other cartridges use the same ciphers? (Xplorer64)

`FCD.md` and `ENCRYPT.md` leave one question open by their own framing: the `.fcd`
image cipher and the WHBX/FCD!/WB123 code cipher were recovered from the PSX
product. FCD shipped others. This is the N64 one, **Xplorer64**, checked against
xpcrypt's two ciphers and its COMP01 container.

Short answer: **COMP01 is shared, the two ciphers are not.** The N64 keeps the same
compression container as the PSX firmware — down to a byte-identical resource
block — but its distributed upgrade file is *plaintext*, its on-chip obfuscation
is a hardware address-line scramble rather than a per-byte value cipher, and its
cheat codes do not use the PSX seed strings. So xpcrypt's `-r` and `-e`/`-d` are
PSX-specific; the thing that crossed product lines is the packer and the people.

Nothing here changes the shipped source. It settles an open question and records a
second data point for COMP01.

## Where the files are

Not in the tree (like `roms/` and `pc/`, these are firmware dumps). Sources:

* `github.com/LibreShark/sharkdumps` — five Xplorer64 builds, each as a matched
  **scrambled** and **unscrambled** pair (1.000E, 1.067E, 1.067G, 1.067U).
* `github.com/RWeick/FCD-0003.1S-Xplorer64` — raw per-chip EEPROM halves plus
  `Scramble.py`/`Unscramble.py`, the address permutation itself.
* the official `xp64_1067g.zip` upgrade (`roms/XP64.ROM`, 262144 bytes).
* `github.com/LibreShark/hammerhead` — `dotnet/src/Nintendo64/N64XpRom.cs`,
  `N64XpScrambler`, `N64XpCrypter.DecryptCodeMethod1`. (It also carries
  `GameBoyColor/GbcXpRom.cs` — FCD made a Game Boy Color Xplorer too, not looked
  at here.)

## 1. No distribution cipher

The PSX contract is: the vendor ships a `.fcd`, which is the plaintext ROM run
through the value cipher (`dec[i] = (enc[i] ^ mask(i)) + addend(i)`,
`mask(i) = i ^ ((i>>1)+0x45)`), and the PC tool decrypts it before flashing
(`FCD.md`). The N64 has no such step. The official upgrade file is plaintext
firmware:

```
XP64.ROM  262144 bytes
  offset 0x00  "(C) 1997/9 FCD Release 1.067G ..."   28 43 29 20 31 39 39 37 2f 39 20 46 43 44 ...
  9x COMP01 inside
  md5(XP64.ROM) == md5(sharkdumps xplorer64-v1.067g-b1930 .bin, the *unscrambled* dump)
```

The upgrade file the user flashes is the unscrambled image byte for byte. There is
no offset keystream over it; xpcrypt's `-r` transform has nothing to match, and
applying it only turns the readable header into noise.

## 2. The obfuscation is on the address bus, not the bytes

What *is* scrambled is the physical EEPROM contents, and the scramble is a
permutation of the low address bits with some inverted — a CPLD wiring trick, not
a computation on the data. From `Unscramble.py`, per 128 KB chip half:

```python
def scramble(addr):
    return (((~addr >> 8) & 0x001) | ((~addr >> 5) & 0x006) | ((~addr >> 6) & 0x008)
          | ((addr << 4) & 0x010) | ((addr >> 6) & 0x020) | ((addr << 3) & 0x040)
          | ((addr << 2) & 0x080) | ((~addr >> 2) & 0x100) | ((addr << 8) & 0x200)
          | ((addr << 6) & 0x400) | ((~addr << 9) & 0x800) | (addr & 0x1F000))
```

`byte-value stays; byte-position moves`. The distributed upgrade image is already
in address order (plaintext), so the scramble matters only between the cartridge
bus and the chip. This is the opposite shape from the `.fcd` cipher, which leaves
positions alone and transforms every byte. Confirmed on the dumps: the
`.scrambled.bin` has no readable `FCD`/`Release` string; the `.bin` does.

## 3. COMP01 crossed over; the resource did too

The N64 firmware is packed with the same COMP01 container `REVERSING.md` §4
documents on the PSX — nine streams in the 1.067 image. More than the format is
shared: one resource block is byte-identical across products. The header is
`"COMP01"` + four escape bytes + a 4-byte big-endian size, and the escape bytes
are chosen per stream from the data (`FINDINGS.md` §5.1b), so an identical header
is an identical stream:

```
COMP01 49 77 64 61 00 00 04 00 01 06     "COMP01Iwda" + size 0x400
  PSX  xteng.dec (2.008)                @0x15BCF
  PSX  xtepro.dec (Pro 2.20)            @0x17218
  PSX  Xploder V2 USA (2.004)           @0x15C5F
  N64  Xplorer64 1.067E                 @0x21BF4
```

Same escape bytes `I w d a`, same 0x400 output size, same following bytes. The
same COMP01 encoder compressed the same resource for both the PSX and N64
cartridges — which is the concrete evidence that the container is one codebase
shared across the product line, not two lookalikes.

## 4. The code cipher did not cross over

The PSX cheat-code cipher is seeded with `"WHBX"`, `"FCD!"` and `" WB123"`
(`REVERSING.md` §6). None of the three appears anywhere in the unscrambled N64
firmware. `hammerhead` implements the N64 code transform as `DecryptCodeMethod1`,
a different routine. So the four PSX code keys and the two payload keys are
PSX-only; the N64 has its own scheme.

## 5. The team, expanded

The PSX header credit is `"FCD = WHB PJH DN MW IN R?"` (`REVERSING.md` §1). The
N64 firmware spells it out:

```
The people at FCD are WHB, PJH, DN, MW, IN, RM, SPGM, and SK
(C) 1997/9 Future Console Design, Ltd
Xplorer64 is not endorsed, licensed nor authorized by Nintendo Co Limited
```

WHB is still first — Wayne Hughes Beckett, whose initials seed the PSX cipher.

## Summary table

```
                 PSX Xplorer/Xploder (V2 & FX)     N64 Xplorer64
distribution     .fcd, value-ciphered              .ROM, plaintext
image cipher     mask 0x45 / addend 0x2C over      none in the file; CPLD
                 file offset (+ FX byte-scramble)  address-line scramble on chip
compression      COMP01                            COMP01 (same, shared "Iwda" block)
code cipher      WHBX / FCD! / WB123, keys 4-7     different (hammerhead "Method1")
```

## Open

* The N64 code cipher (`DecryptCodeMethod1`) and its database format were not read
  here; only that they are not the PSX ones.
* The Game Boy Color Xplorer (`GbcXpRom.cs`) is a third product line, unlooked-at.
* Whether the N64 COMP01 is bit-for-bit the PSX decoder (the same `comp01.py`
  reads it) was not run to completion — the shared `"Iwda"` header is the evidence
  offered, not a full round-trip.
